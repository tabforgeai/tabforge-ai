================================================================================
  EasyAI - Developer Guide
  A simple Java API for adding AI to your application
================================================================================

  Demo Application
  ----------------
  A working example is available at: https://github.com/tabforgeai/tabforge-ai-demo

  What is EasyAI?
  ---------------
  EasyAI is an abstraction layer over LangChain4J. It hides all the low-level
  complexity behind a simple builder-pattern API. You don't need to know anything
  about ChatModel, AiServices, ToolSpecification, or EmbeddingStore.

  You just need to know 6 things:
    1. EasyAI.chat()       - for simple conversations
    2. EasyAI.assistant()  - for smart assistants that can call your Java code
    3. @EasyRAG            - for AI that answers questions from your documents
    4. EasyAI.agent()      - for autonomous multi-step task execution
    5. EasyAI.indexer()    - to store documents in a vector database (Milvus)
                             for persistent, large-scale RAG
    6. EasyAI.extract()    - to turn unstructured text or documents into
                             typed Java objects (records / POJOs)


================================================================================
  SETUP (5 minutes)
================================================================================

  Step 1: Maven (already configured in pom.xml)
  ------------------------------------------------
  The following dependencies are included:
    - langchain4j           (core AI services)
    - langchain4j-open-ai   (OpenAI provider)
    - langchain4j-easy-rag   (document processing + local embedding model for RAG)
    - langchain4j-milvus     (persistent vector store - see USE CASE 9)

  Step 2: Configuration
  ------------------------------------------------
  Create src/main/resources/easyai.properties in your application:

    easyai.provider=openai
    easyai.api-key=sk-YOUR-OPENAI-API-KEY
    easyai.model-name=gpt-4o-mini

  Maven packages src/main/resources/ into WEB-INF/classes/ inside your WAR,
  where EasyAI picks it up from the classpath automatically.

  That's it. You're ready to use EasyAI.

  Alternative: Use local Ollama (free, no API key needed)
  ------------------------------------------------
    1. Install Ollama from https://ollama.ai
    2. Run: ollama pull llama3
    3. In src/main/resources/easyai.properties:
         easyai.provider=ollama
         easyai.model-name=llama3


================================================================================
  USE CASE 1: Simple Chat
================================================================================

  The simplest way to talk to AI. Send a message, get a response.

  --- Minimal Example ---

    Conversation chat = EasyAI.chat().build();
    String answer = chat.send("What is the capital of France?");
    System.out.println(answer);
    // Output: "The capital of France is Paris."

  --- With Memory (AI Remembers Previous Messages) ---

    Conversation chat = EasyAI.chat()
        .withMemory(20)    // remember last 20 messages
        .build();

    chat.send("My name is John");
    String answer = chat.send("What is my name?");
    // answer: "Your name is John."

  --- With a System Message (Set AI Personality) ---

    Conversation chat = EasyAI.chat()
        .withMemory(20)
        .withSystemMessage("You are a friendly Java tutor. "
            + "Explain concepts simply with code examples.")
        .build();

    String answer = chat.send("What is a HashMap?");
    // AI responds as a Java tutor with examples

  --- Override Config Per-Conversation ---

    Conversation chat = EasyAI.chat()
        .withProvider("ollama")
        .withModel("llama3")
        .withBaseUrl("http://localhost:11434/v1/")
        .withTemperature(0.3)   // less creative, more precise
        .withMaxTokens(500)     // shorter answers
        .withMemory(10)
        .build();


================================================================================
  USE CASE 2: AI Assistant (Interface-Based)
================================================================================

  Define a Java interface. EasyAI creates an AI implementation at runtime.

  --- Step 1: Define the Interface ---

    @EasyAIAssistant(systemMessage = "You are a helpful code reviewer")
    public interface CodeReviewer {
        String review(String code);
    }

  --- Step 2: Build and Use ---

    CodeReviewer reviewer = EasyAI.assistant(CodeReviewer.class).build();

    String feedback = reviewer.review(
        "public void processData(List data) {\n"
      + "    for (int i = 0; i < data.size(); i++) {\n"
      + "        System.out.println(data.get(i));\n"
      + "    }\n"
      + "}"
    );
    // AI reviews the code and gives feedback


================================================================================
  USE CASE 3: AI Assistant with Tools (AI Calls Your Java Methods)
================================================================================

  This is the most powerful feature. You give the AI access to your existing
  Java services, and it decides when to call them based on the user's question.

  YOUR SERVICE CLASSES DON'T NEED ANY AI ANNOTATIONS. They are plain Java.

  --- Step 1: Your Existing Service (plain POJO/EJB) ---

    public class OrderService {

        public String findOrder(String orderId) {
            // your existing database logic
            return "Order " + orderId + ": shipped, arrives tomorrow";
        }

        public String cancelOrder(String orderId) {
            // your existing logic
            return "Order " + orderId + " has been cancelled";
        }

        public List<String> getOrdersByCustomer(String email) {
            // your existing logic
            return List.of("ORD-001", "ORD-002", "ORD-003");
        }
    }

  --- Step 2: Define the Assistant Interface ---

    @EasyAIAssistant(systemMessage = "You are an e-commerce support bot. "
        + "Help customers with their orders.")
    public interface SupportBot {
        String ask(String question);
    }

  --- Step 3: Wire Them Together ---

    OrderService orderService = new OrderService();
    UserService userService = new UserService();

    SupportBot bot = EasyAI.assistant(SupportBot.class)
        .withTools(orderService, userService)   // pass any number of services
        .build();

  --- Step 4: Use It ---

    String answer = bot.ask("Where is my order #12345?");
    // Behind the scenes:
    //   1. AI reads the question
    //   2. AI decides to call orderService.findOrder("12345")
    //   3. AI gets the result from your method
    //   4. AI formats a nice response for the user

    answer = bot.ask("Cancel order #12345");
    // AI calls orderService.cancelOrder("12345") automatically

    answer = bot.ask("Show me all orders for john@example.com");
    // AI calls orderService.getOrdersByCustomer("john@example.com")


  --- Optional: Add @EasyTool for Better Descriptions ---

  If the AI is picking the wrong method, add @EasyTool to help it:

    public class OrderService {

        @EasyTool("Finds an order by its ID and returns its current status")
        public String findOrder(String orderId) { ... }

        @EasyTool("Cancels an active order. Only works for unshipped orders.")
        public String cancelOrder(String orderId) { ... }
    }

  Note: @EasyTool is optional. Without it, the AI uses the method name
  as the description. It works fine in most cases.


================================================================================
  USE CASE 4: Document-Powered AI (RAG)
================================================================================

  Let the AI answer questions based on your PDF, DOCX, or TXT files.
  The AI reads your documents and gives answers based on their content.

  There are three ways to provide documents, depending on where they come from:

    A) @EasyRAG annotation     - for static files on classpath or disk
    B) .withRAG(path...)       - for file paths known at runtime
    C) .withRAG(DocumentSource...) - for content loaded as byte[] from
                                     a DMS, database, REST API, or upload

  Supported formats: PDF, DOCX, DOC, PPTX, TXT, HTML (via Apache Tika).


  --- A) @EasyRAG Annotation (Static Files) ---

  Best for: documents packaged with your app that don't change at runtime.

  Step 1: Place your document on the classpath.
  Put your file (e.g., company-policy.pdf) in:
    src/main/resources/     (standard Maven — Maven packages it into WEB-INF/classes/)

  Step 2: Define the interface with @EasyRAG.

    @EasyRAG(source = "classpath:company-policy.pdf")
    @EasyAIAssistant(systemMessage = "Answer based on the company policy")
    public interface PolicyBot {
        String ask(String question);
    }

  Step 3: Build and use.

    PolicyBot bot = EasyAI.assistant(PolicyBot.class).build();

    String answer = bot.ask("How many vacation days do employees get?");
    // AI searches the PDF and answers based on the actual content

  Multiple documents:

    @EasyRAG(source = {
        "classpath:docs/installation-guide.pdf",
        "classpath:docs/user-manual.pdf",
        "classpath:docs/faq.txt"
    })
    @EasyAIAssistant(systemMessage = "Help users with product documentation")
    public interface HelpDeskBot {
        String ask(String question);
    }

  Loading from file system:

    @EasyRAG(source = "file:C:/data/contracts/terms.pdf")

  Tuning RAG:

    @EasyRAG(
        source = "classpath:manual.pdf",
        maxResults = 5,     // include top 5 relevant segments (default: 3)
        minScore = 0.7      // only highly relevant segments (default: 0.5)
    )


  --- B) .withRAG(path...) (File Paths at Runtime) ---

  Best for: documents on disk whose paths come from configuration,
  servlet context, or are determined at runtime.

    // Path from application config, database, or servlet context
    String docPath = servletContext.getRealPath("/WEB-INF/docs/policy.pdf");

    PolicyBot bot = EasyAI.assistant(PolicyBot.class)
        .withRAG(docPath)
        .build();

  Multiple documents:

    PolicyBot bot = EasyAI.assistant(PolicyBot.class)
        .withRAG(
            "file:C:/app-data/docs/policy.pdf",
            "file:C:/app-data/docs/faq.pdf"
        )
        .build();

  With tuning parameters:

    PolicyBot bot = EasyAI.assistant(PolicyBot.class)
        .withRAG(
            new String[]{docPath1, docPath2},
            5,     // maxResults: top 5 relevant segments
            0.7    // minScore: 70%+ relevance only
        )
        .build();


  --- C) .withRAG(DocumentSource...) (Bytes from DMS / Database / API) ---

  Best for: enterprise applications where documents are stored in a DMS,
  database (BLOB), or fetched via REST API. The content arrives as byte[],
  not as a file on disk. This is the most common scenario in real-world
  web applications.

  The key class is DocumentSource, which wraps byte[] content with a file name.
  The file name extension (.pdf, .docx, .txt) tells the parser how to read it.

  Creating a DocumentSource:
    DocumentSource.of("name.pdf", byteArray)      - from raw bytes
    DocumentSource.ofText("name", stringContent)   - from plain text

  Example: Document from a DMS:

    byte[] pdfBytes = dmsClient.downloadDocument("DOC-12345");

    PolicyBot bot = EasyAI.assistant(PolicyBot.class)
        .withRAG(DocumentSource.of("policy.pdf", pdfBytes))
        .build();

    bot.ask("What is the refund policy?");

  Example: Document from a database BLOB:

    byte[] content = resultSet.getBytes("document_content");
    String fileName = resultSet.getString("file_name");   // e.g. "terms.pdf"

    PolicyBot bot = EasyAI.assistant(PolicyBot.class)
        .withRAG(DocumentSource.of(fileName, content))
        .build();

  Example: Plain text (no file needed at all):

    String rulesText = configService.loadBusinessRules();

    PolicyBot bot = EasyAI.assistant(PolicyBot.class)
        .withRAG(DocumentSource.ofText("rules", rulesText))
        .build();

  Example: Multiple documents from different sources:

    DocumentSource fromDms   = DocumentSource.of("policy.pdf",
                                   dmsClient.download("policy"));
    DocumentSource fromDb    = DocumentSource.of("terms.docx",
                                   resultSet.getBytes("doc_content"));
    DocumentSource fromText  = DocumentSource.ofText("extra-rules",
                                   "Additional rules: no remote work on Fridays.");
    DocumentSource fromApi   = DocumentSource.of("faq.pdf",
                                   restClient.get("/api/docs/faq").body());

    PolicyBot bot = EasyAI.assistant(PolicyBot.class)
        .withRAG(fromDms, fromDb, fromText, fromApi)
        .build();

  With tuning parameters:

    PolicyBot bot = EasyAI.assistant(PolicyBot.class)
        .withRAG(
            List.of(fromDms, fromDb),
            5,     // maxResults: top 5 relevant segments
            0.7    // minScore: 70%+ relevance only
        )
        .build();


  --- Which approach should I use? ---

    Source of documents               Use this
    --------------------------------  ----------------------------------
    Static files in your project      @EasyRAG annotation
    Files on disk, path from config   .withRAG("file:...")
    DMS (Alfresco, SharePoint, ...)   .withRAG(DocumentSource.of(...))
    Database BLOB                     .withRAG(DocumentSource.of(...))
    REST API response                 .withRAG(DocumentSource.of(...))
    User-uploaded file (byte[])       .withRAG(DocumentSource.of(...))
    Plain text / String               .withRAG(DocumentSource.ofText(...))

  Note: every approach above is EPHEMERAL — documents are embedded into an
  in-memory store on each build() and vanish when the app stops. For a large or
  shared document set that must survive restarts, embed once into a persistent
  vector database instead — see USE CASE 9 (Milvus).


================================================================================
  USE CASE 5: Jakarta EJB Beans as Tools
================================================================================

  EasyAI fully supports Jakarta EJB beans (@Stateless, @Stateful, @Singleton)
  as tool objects. If you inject an EJB via @Inject and pass it to withTools(),
  everything works automatically - EasyAI detects the EJB proxy and discovers
  the business methods from the actual bean class.

  The method calls still go through the EJB proxy, so container services
  (transactions, security, interceptors) work exactly as they would normally.

  --- Example: @Stateless EJB as a Tool ---

    @Stateless
    public class OrderService {

        @PersistenceContext
        private EntityManager em;

        public String findOrder(String orderId) {
            Order order = em.find(Order.class, orderId);
            return order != null ? order.toString() : "Order not found";
        }

        public String cancelOrder(String orderId) {
            // runs inside a JTA transaction automatically
            Order order = em.find(Order.class, orderId);
            order.setStatus("CANCELLED");
            return "Order " + orderId + " cancelled";
        }
    }

    @EasyAIAssistant(systemMessage = "You are an e-commerce support bot")
    public interface SupportBot {
        String ask(String question);
    }

    // In your CDI bean / JSF controller / REST endpoint:
    @Inject OrderService orderService;     // EJB proxy from CDI container

    SupportBot bot = EasyAI.assistant(SupportBot.class)
        .withTools(orderService)           // just pass the injected proxy
        .build();

    bot.ask("Cancel my order #12345");
    // AI calls orderService.cancelOrder("12345") through the EJB proxy
    // -> transaction is managed by the container, just like a normal EJB call

  --- Example: @Singleton Cache + @Stateless Service Together ---

    @Singleton
    public class CacheService {
        private final Map<String, String> cache = new ConcurrentHashMap<>();

        public String getCachedValue(String key) {
            return cache.getOrDefault(key, "not found");
        }
    }

    @Stateless
    public class ReportService {

        public String generateReport(String reportType) {
            // heavy transactional work...
            return "Report: ...";
        }
    }

    // Inject both EJBs
    @Inject CacheService cacheService;
    @Inject ReportService reportService;

    SupportBot bot = EasyAI.assistant(SupportBot.class)
        .withTools(cacheService, reportService)   // mix different EJB types
        .build();

  --- Example: @Stateful Shopping Cart ---

    @Stateful
    public class CartService {

        private final List<String> items = new ArrayList<>();

        public String addItem(String itemName) {
            items.add(itemName);
            return "Added " + itemName + ". Cart has " + items.size() + " items.";
        }

        public String getCartContents() {
            return "Cart: " + String.join(", ", items);
        }
    }

    @Inject CartService cartService;

    ShoppingBot bot = EasyAI.assistant(ShoppingBot.class)
        .withTools(cartService)
        .build();

    bot.ask("Add a blue t-shirt to my cart");
    bot.ask("What's in my cart?");

  --- Key Points ---

    - All three EJB types are supported: @Stateless, @Stateful, @Singleton
    - Just inject via @Inject and pass to withTools() - nothing else needed
    - Transactions, security, and interceptors work normally (calls go
      through the container proxy)
    - You can mix EJBs with plain POJOs in the same withTools() call
    - No special annotations, no JNDI lookup, no extra configuration


================================================================================
  USE CASE 6: Combined - Tools + RAG
================================================================================

  You can combine tools (including EJB beans) AND documents on the same assistant.

  With annotation:

    @EasyRAG(source = "classpath:product-catalog.pdf")
    @EasyAIAssistant(systemMessage = "You are a sales assistant. "
        + "Use the product catalog for information and the inventory "
        + "service to check stock.")
    public interface SalesBot {
        String ask(String question);
    }

    SalesBot bot = EasyAI.assistant(SalesBot.class)
        .withTools(inventoryService, pricingService)
        .build();

    bot.ask("Is the XYZ laptop in stock and what does it cost?");
    // AI reads the product catalog AND calls inventoryService.checkStock()

  With DocumentSource (e.g. catalog from DMS + live inventory service):

    byte[] catalogBytes = dmsClient.download("product-catalog");

    SalesBot bot = EasyAI.assistant(SalesBot.class)
        .withRAG(DocumentSource.of("catalog.pdf", catalogBytes))
        .withTools(inventoryService, pricingService)
        .build();


================================================================================
  USE CASE 7: CDI / Jakarta EE Integration
================================================================================

  In a Jakarta EE application (GlassFish, WildFly, Payara, etc.),
  assistants annotated with @EasyAIAssistant are automatically injectable.
  The CDI extension (EasyAIExtension) creates one ApplicationScoped instance
  per assistant interface.


  --- A) Simple injection (no tools) ---

    @EasyAIAssistant(systemMessage = "You are a helpful Java tutor")
    public interface JavaTutor {
        String ask(String question);
    }

    // Just inject - no build() needed!
    @Inject JavaTutor tutor;

    public String handleQuestion(String userQuestion) {
        return tutor.ask(userQuestion);
    }


  --- B) Injection with auto-wired tools ---

  Declare which CDI/EJB beans should be wired as tools directly in the
  annotation. The CDI extension resolves their live instances automatically.
  No manual withTools() call needed.

    @EasyAIAssistant(
        systemMessage = "You are an e-commerce support bot",
        tools = {OrderService.class, InventoryService.class}
    )
    public interface SupportBot {
        String ask(String question);
    }

    // OrderService and InventoryService are resolved from the CDI container
    // and wired as tools automatically - equivalent to:
    //   EasyAI.assistant(SupportBot.class)
    //       .withTools(orderService, inventoryService)
    //       .build();
    @Inject SupportBot bot;

    public String handleQuestion(String userQuestion) {
        return bot.ask(userQuestion);
    }

  Works with all CDI/EJB bean types:
    tools = {OrderService.class}               // @Stateless EJB
    tools = {CartService.class}                // @Stateful EJB
    tools = {CacheService.class}               // @Singleton EJB
    tools = {MyAppScopedBean.class}            // @ApplicationScoped CDI bean
    tools = {OrderService.class, CacheService.class}  // mix of types


  --- C) When to use @Inject vs. manual build() ---

    Scenario                                Use
    ------------------------------------    ----------------------------------
    Simple assistant, no tools              @Inject (annotation only)
    Tools known at compile time             @Inject + tools = {...} attribute
    Tools or config change at runtime       EasyAI.assistant(...).withTools(...).build()
    RAG with byte[] from DMS/DB/API         EasyAI.assistant(...).withRAG(...).build()
    Testing with mock model                 EasyAI.assistant(...).withChatModel(mock).build()


================================================================================
  USE CASE 8: EasyAgent (Autonomous Multi-Step Task Execution)
================================================================================

  An EasyAgent goes beyond a single question-and-answer. You give it a complex
  task in natural language, and it autonomously plans which service methods to
  call, executes them in the right order, uses the result of each step to
  decide what to do next, and adapts if a step fails.

  You don't write any orchestration code. The agent plans and executes at
  runtime.

  --- Key Concepts ---

    withServices()       - registers your Java services (same as withTools()
                           in AssistantBuilder, but semantically clearer)
    withMaxSteps(n)      - caps the number of service calls per task execution
                           (strongly recommended — default is 10)
    withPlanningPrompt() - injects a built-in system message that instructs
                           the LLM to think step by step before acting
    withStepListener()   - callback invoked after each service call, giving you
                           full visibility into what the agent did

  --- Minimal Example ---

    EasyAgent agent = EasyAI.agent()
        .withServices(inventoryService, orderService)
        .withMaxSteps(10)
        .build();

    String result = agent.execute("Order 2 laptops for user U123.");

  --- Full Example with Planning and Trace ---

    @Inject InventoryService inventoryService;
    @Inject PaymentService   paymentService;
    @Inject OrderService     orderService;
    @Inject ShippingService  shippingService;

    EasyAgent agent = EasyAI.agent()
        .withServices(inventoryService, paymentService, orderService, shippingService)
        .withMaxSteps(10)
        .withPlanningPrompt(true)
        .withStepListener(step ->
            log.info("[AGENT] Step {}: {}({}) -> {}",
                step.stepNumber(), step.toolName(),
                step.arguments(),  step.result()))
        .build();

    String result = agent.execute(
        "Order 2 laptops for user U123, apply loyalty credit, " +
        "deliver to Belgrade. If out of stock, use warehouse WH-EU."
    );

  What the agent executes autonomously:
    Step 1: inventoryService.checkStock("laptop", 2)              -> false
    Step 2: inventoryService.getFromWarehouse("laptop", 2, "WH-EU") -> "reserved:REF-88"
    Step 3: paymentService.applyLoyaltyCredit("U123")             -> 150.0
    Step 4: paymentService.processPayment(850.0, "loyalty+card")  -> "PAY-991"
    Step 5: orderService.createOrder("laptop x2", "REF-88", "PAY-991") -> "ORD-441"
    Step 6: shippingService.scheduleDelivery("ORD-441", "Belgrade") -> "delivery scheduled"

  None of this flow was coded manually. The agent adapted (used fallback
  warehouse when stock was unavailable) entirely on its own.

  --- Step Listener ---

  The StepListener receives an AgentStep record after each tool call:

    step.stepNumber()  - sequence number starting from 1
    step.toolName()    - name of the service method that was called
    step.arguments()   - JSON string of arguments passed to the method
    step.result()      - string result returned by the method

  When a tool throws an exception, the result is a structured error message
  that the agent can interpret:
    "TOOL_ERROR | tool=checkStock | error=DB timeout | suggestion=Try a different approach..."

  --- Max Steps Limit ---

  withMaxSteps(n) is strongly recommended. When the step limit is reached,
  the agent receives:
    "MAX_STEPS_REACHED: You have reached the maximum of N tool calls allowed.
     Please provide a final answer based on the information gathered so far."
  The agent then returns a final answer without further tool calls.

  Without this limit, a complex task could trigger many sequential calls,
  significantly increasing token usage and cost.

  --- withPlanningPrompt(true) ---

  Injects this system message (prepended to any custom system message):
    "You are a planning agent. When given a complex task:
     1. Think step by step and identify which tools to call and in what order.
     2. Execute the steps sequentially.
     3. Use the result of each step to inform the next decision.
     4. If a step fails, adjust your plan and try an alternative approach.
     5. Once done, provide a clear final answer."

  Improves reliability for complex tasks with conditional branching.

  --- EasyAgent vs. EasyAI.assistant() ---

    Scenario                                Use
    ------------------------------------    ----------------------------------
    Single question, structured answer      EasyAI.assistant()
    Multi-step task, autonomous execution   EasyAI.agent()
    Workflow with conditional branching     EasyAI.agent()
    Known fixed sequence of calls           EasyAI.assistant() or manual code

  --- Important Notes ---

  1. Transactions: EasyAgent does not manage transactions across steps.
     If the agent calls payment.process() and then fails on the next step,
     the payment will not be rolled back. Design your services to be
     idempotent or provide compensating transactions where needed.

  2. Determinism: the LLM may make different decisions for the same input.
     Do not use EasyAgent for financial transactions without a human-in-the-loop
     confirmation step.

  3. Token cost: each tool call adds tokens to the conversation. With 10 steps
     and GPT-4o, one agent.execute() can cost significantly more than one
     bot.ask(). Monitor usage accordingly.


================================================================================
  USE CASE 9: Persistent Knowledge Base with Milvus (Index Once, Ask Forever)
================================================================================

  USE CASE 4 (RAG) loads and embeds your documents fresh every time you build an
  assistant, into an in-memory store that disappears when the app restarts. That
  is perfect for a handful of small, static documents.

  But real applications accumulate thousands of documents, shared across users
  and surviving restarts. Re-reading and re-embedding them on every boot is slow
  and wasteful. You want to embed each document ONCE, store the vectors in a real
  database, and have every assistant — in every session, on every server node —
  query that same store instantly.

  That is what a persistent vector store gives you. EasyAI integrates Milvus
  (https://milvus.io), a production-grade vector database, in two halves:

    EasyAI.indexer()   - the WRITE side: put documents into Milvus (once)
    .withMilvus(...)   - the READ side:  let an assistant query that Milvus

  Think of it like a database: indexer() is the INSERT, withMilvus() is the
  SELECT. You populate the collection once (a batch job, or on each upload);
  everyone reads from it forever after.


  --- Scenario A: A company knowledge base indexed overnight ---

  Your support team has 5,000 policy PDFs, manuals, and FAQs. A nightly batch job
  embeds any new or changed documents into Milvus. Every app instance then answers
  employee questions against that shared collection — no document is re-embedded
  at request time, and a server restart costs nothing.

  Nightly indexing job (runs once, not per request):

    int indexed = EasyAI.indexer()
        .toMilvus("milvus.internal", 19530, "company_kb")
        .index(
            "file:/var/data/docs/policy.pdf",
            "file:/var/data/docs/handbook.pdf",
            "classpath:faq.txt"
        );
    log.info("Indexed {} documents into the knowledge base", indexed);

  Any assistant, any time, any server node reads from the same store:

    @EasyAIAssistant(systemMessage = "Answer using the company knowledge base.")
    public interface KbBot {
        String ask(String question);
    }

    KbBot bot = EasyAI.assistant(KbBot.class)
        .withMilvus("milvus.internal", 19530, "company_kb")
        .build();

    bot.ask("How many vacation days do full-time employees get?");
    // Instant - no documents are loaded or embedded at request time


  --- Scenario B: Users upload documents that stay searchable ---

  In a web app, users upload contracts, reports, or manuals. You don't have a file
  path - you have the uploaded bytes. Index them straight into Milvus on upload,
  and every future question searches the whole accumulated corpus.

  On upload (bytes, not a file path):

    // e.g. PrimeFaces UploadedFile, a Servlet Part, a DMS download, a DB BLOB
    byte[] bytes    = uploadedFile.getContent();
    String fileName = uploadedFile.getFileName();   // "contract-2026.pdf"

    EasyAI.indexer()
        .toMilvus("localhost", 19530, "user_documents")
        .index(DocumentSource.of(fileName, bytes));

  Later - the assistant answers across everything uploaded so far:

    DocsBot bot = EasyAI.assistant(DocsBot.class)
        .withMilvus("localhost", 19530, "user_documents")
        .build();

    bot.ask("What is the termination notice period in the 2026 contract?");

  The same DocumentSource you already know from USE CASE 4 works here - bytes from
  a DMS, a database BLOB, a REST API, or plain text via
  DocumentSource.ofText(name, text). You can index many at once:

    EasyAI.indexer()
        .toMilvus("localhost", 19530, "user_documents")
        .index(
            DocumentSource.of("policy.pdf", dmsClient.download("policy")),
            DocumentSource.of("terms.docx", resultSet.getBytes("doc_content")),
            DocumentSource.ofText("extra-rules", "No remote work on Fridays.")
        );


  --- Configuration (optional): keep connection details out of code ---

  Put Milvus settings in easyai.properties and call the no-argument variants:

    easyai.milvus.host=localhost
    easyai.milvus.port=19530
    easyai.milvus.collection=company_kb
    easyai.milvus.dimension=384

    EasyAI.indexer().toMilvus().index(...);             // settings from properties
    EasyAI.assistant(KbBot.class).withMilvus().build();

  The dimension (384) must match the embedding model. EasyAI uses the local model
  bundled with langchain4j-easy-rag (no API key, runs offline) for BOTH indexing
  and retrieval, so dimensions line up automatically. If you switch embedding
  models, set the matching dimension or Milvus rejects the inserts.


  --- Tuning retrieval ---

    KbBot bot = EasyAI.assistant(KbBot.class)
        .withMilvus(
            MilvusConfig.of("localhost", 19530, "company_kb"),
            5,      // maxResults: top 5 relevant segments (default 3)
            0.7     // minScore:  70%+ relevance only      (default 0.5)
        )
        .build();


  --- Ephemeral RAG (USE CASE 4) vs Persistent Milvus (this one) ---

    Question                                 In-memory RAG    Milvus
    ---------------------------------------  ---------------  ---------------
    A few small static docs                  yes              overkill
    Thousands of docs / large corpus         slow             yes
    Survives app restart                     no (re-embeds)   yes
    Shared across sessions / server nodes    no               yes
    Embed once, query many times             no               yes
    Zero infrastructure to run               yes              needs Milvus

  When set, .withMilvus(...) takes precedence over .withRAG(...) and @EasyRAG on
  the same assistant.

  Note on freshness: Milvus is eventually consistent - a document you just indexed
  may take a moment to become searchable. For "index then immediately query"
  flows, allow a brief delay (or re-query).


================================================================================
  USE CASE 10: Structured Extraction (Text/Document -> Typed Java Object)
================================================================================

  Everything above produces text. This one produces TYPED DATA: hand EasyAI an
  email, a chat message, or a PDF, and get back a populated Java record or POJO.

  This is the bridge from the unstructured / AI world into your normal,
  typed-Java world. Once .from(...) returns, the AI is out of the picture - you
  hold a plain Invoice / Order / Candidate object that your existing services,
  JPA entities, and PrimeFaces forms already know how to handle.

    record Invoice(String vendor, String invoiceNumber, LocalDate date,
                   BigDecimal total, List<LineItem> items) {}

    // From free text:
    Invoice inv = EasyAI.extract(Invoice.class).from(emailBody);

    // From a document's bytes - parses (Tika) AND extracts in one call:
    Invoice inv = EasyAI.extract(Invoice.class)
                        .from(DocumentSource.of("invoice.pdf", pdfBytes));

    // From here on it is just data:
    em.persist(inv);
    if (inv.total().compareTo(LIMIT) > 0) approvalService.require(inv);

  Supports records and POJOs, nested objects, lists, enums, and java.time types.
  Robustness is built in: malformed model output is retried automatically.


  --- Scenario A: Turn every inbound email into a typed Order ---

  A sales mailbox receives free-form order emails ("Hi, please send 3 keyboards
  and 2 monitors to our Belgrade office, invoice to ACME d.o.o ..."). Instead of
  parsing strings by hand, extract a typed Order and feed it straight into your
  existing order pipeline.

    record OrderLine(String product, int quantity) {}
    record Order(String customer, String shipTo, List<OrderLine> lines) {}

    Order order = EasyAI.extract(Order.class).from(emailBody);

    orderService.create(order);     // your existing EJB / service, unchanged

  No prompt engineering, no JSON parsing, no brittle regex - the email becomes an
  Order object and the rest of your application proceeds as normal.


  --- Scenario B: Accounts payable - drop a PDF invoice, get a validated entity ---

  Users upload supplier invoices (PDF) in a web app. Extract a validated Invoice
  ready to persist and route for approval. Turn on .validate() to enforce Jakarta
  Bean Validation constraints declared on the target type.

    public class Invoice {
        @NotBlank String vendor;
        @NotBlank String invoiceNumber;
        @NotNull  LocalDate date;
        @Positive BigDecimal total;
    }

    // e.g. PrimeFaces UploadedFile
    byte[] bytes    = uploadedFile.getContent();
    String fileName = uploadedFile.getFileName();   // "invoice-4042.pdf"

    Invoice inv = EasyAI.extract(Invoice.class)
                        .validate()                 // enforce @NotBlank/@NotNull/@Positive
                        .from(DocumentSource.of(fileName, bytes));

    invoiceRepository.save(inv);
    approvalQueue.submit(inv);

  If the document is missing a required field or the total is not positive,
  .validate() throws ExtractionException with a clear message - so bad data never
  reaches your database.


  --- Options ---

    .withRetries(n)   - extra attempts if the model returns malformed JSON
                        (default 2; set 0 to disable)
    .validate()       - run Jakarta Bean Validation on the result; requires a
                        Bean Validation provider on the classpath (present in a
                        Jakarta EE container). Throws ExtractionException on a
                        violation.
    .withModel(...), .withApiKey(...), .withProvider(...), .withBaseUrl(...),
    .withTemperature(...)   - same per-call config overrides as elsewhere
                              (extraction defaults to temperature 0.0).

  Tip: extraction pairs naturally with the other use cases - extract a record
  from a RAG-retrieved document, or have an agent call a service that extracts.


================================================================================
  USE CASE 11: Ambient Activity Memory (The Assistant Knows What You Just Did)
================================================================================

  Every use case above answers the exact question the user types. But people
  rarely spell out the context: they open an order on screen and then ask
  "cancel this one", or switch to a tab and ask "what am I looking at?". A
  colleague glancing at your screen would simply know. Ambient Activity Memory
  gives your assistant that same over-the-shoulder awareness.

  --- The simple example ---

    The user opens order ORD-002 in the UI, then types:   "cancel this"
    The assistant cancels ORD-002 - even though the message never named it.

  It works because the act of opening the order was recorded onto a short
  activity timeline, and that timeline was handed to the model as context just
  before it answered. The model read "recently viewed order ORD-002" and
  resolved "this" on its own.


  --- How it works (in one picture) ---

    user does something in the UI
        -> recorded as a UserActivityEvent (what verb, which entity, which tab)
        -> kept in a small, per-session, in-memory timeline (ActivityStore)

    user asks the assistant something
        -> just before the model runs, the recent slice of that timeline is
           rendered into the SYSTEM message (ActivityContext.render())
        -> the model sees "recently viewed order ORD-002" and resolves "this"

  This is the mirror image of the live event stream (AI -> UI). Here the arrow
  points the other way, UI -> AI: you capture events WHEN they happen, and read
  a compact, recent slice at the MOMENT the AI is called. The model never sees
  raw clicks - only a short, human-readable briefing of the last few actions.

  Privacy by design: the timeline lives in memory, is scoped per session,
  bounded to the most recent N events, and evaporates when the session ends.
  Only labels and ids are stored - never raw clicks or screen contents.


  --- What you do: 2 steps ---

  STEP 1: Capture activity (opt-in - nothing is recorded unless you ask).

  There are two sources of activity; use either or both.

  (a) Navigation - "which tab is the user on".
      Add trackActivity = true to your @DynTab. Opening or re-selecting the tab
      is then recorded automatically. No other code.

        @DynTab(name = "OrdersDynTab", uniqueIdentifier = "Orders",
                title = "Orders", includePage = "/WEB-INF/include/orders.xhtml",
                trackActivity = true)              // <-- opt in
        public class OrdersBean extends BaseDyntabCdiBean { ... }

  (b) Business actions - "which entity the user acted on".
      Annotate a method with @ActivityTracked. When it is called, an event is
      recorded, tagging the entity whose id is in the named parameter.

        @ApplicationScoped
        public class OrderActivityService {

            @ActivityTracked(type = Type.BUSINESS_ACTION, verb = "view",
                             entityType = "order", entityIdParams = "orderId")
            public String viewOrder(String orderId) {
                return loadOrder(orderId);         // your normal logic
            }
        }

  Both write through the same ActivityRecorder facade, which stamps each event
  with the current session and tab. You can also record by hand for things an
  annotation can't express:

        @Inject ActivityRecorder recorder;
        recorder.record(Type.NOTE, "note", null, "free-text note the user typed");


  STEP 2: Make the assistant aware - .withActivityContext(...).

  Build an ActivityContext describing WHICH slice of the timeline to inject, and
  pass it to any assistant or conversation. It is re-read fresh on every call.

        @Inject ActivityStore activityStore;       // the default in-memory store

        ActivityContext ctx = ActivityContext.of(activityStore)
            .forSession(sessionId)        // scope to this user's session
            .forTab(tabId)                // (optional) scope to one tab
            .window(Duration.ofMinutes(30))  // (optional) only the last 30 min
            .limit(20)                    // (optional) at most N events (default 20)
            .build();

        OrdersAssistant assistant = EasyAI.assistant(OrdersAssistant.class)
            .withTools(orderService)      // so it can ACT on "this"
            .withActivityContext(ctx)     // so it KNOWS what "this" is
            .build();

        assistant.ask("cancel this");     // resolves to the order just viewed

  The same builder call works on a plain conversation:

        Conversation chat = EasyAI.chat()
            .withActivityContext(ctx)
            .build();


  --- Two ways to scope it (both shown in the demo) ---

  Per-tab deixis - act on "this":

        ActivityContext.of(store).forSession(s).forTab(t).build()
        + .withTools(...)        ->  "cancel this order"

      The context is narrowed to one tab, so "this" is unambiguous.

  Session-wide orientation - know "where am I":

        ActivityContext.of(store).forSession(s).build()   (no forTab)
        ->  "what tab am I on?", "what have I been looking at?"

      The context spans every tracked tab, so the assistant can report the
      user's navigation across the whole application.


  --- How the briefing looks to the model ---

  The default renderer turns the timeline into a short, plain block, e.g.:

        Recent user activity in this tab (oldest first):
        - 14:02 open Orders
        - 14:03 view order ORD-002

  That text is appended to your system message. Supply your own format with
  .renderer(...) on the builder if you want a different style.


  --- Important notes ---

  1. Opt-in only. Without @DynTab(trackActivity=true) or @ActivityTracked,
     nothing is captured. The feature is silent until you switch it on.

  2. Scope must line up. The ActivityContext reads with forSession/forTab; the
     recorder stamps each event with the current session and tab. In TabForge
     the tab id is getDynTabId() - pass exactly that to forTab(...).

  3. In-memory and ephemeral by default. Activity is held in a per-session ring
     buffer (ActivityStore SPI, InMemoryActivityStore default, ~200 events per
     session) and is gone when the app stops. Provide your own ActivityStore
     bean to back it with a database if you need durability.

  4. Recording never breaks the user's action. A failure to record is swallowed
     and logged - tab navigation and your service calls are unaffected.

  @EasyAIAssistant
    Where:    on an interface
    Purpose:  marks it as an AI assistant
    Attribute: systemMessage (optional) - defines AI personality

  @EasyTool
    Where:    on a public method (in your service class)
    Purpose:  adds a description to help the AI understand the method
    Note:     OPTIONAL - methods work without it

  @EasyRAG
    Where:    on an interface (alongside @EasyAIAssistant)
    Purpose:  loads documents for document-powered AI (static paths)
    Attributes:
      source     - file paths (classpath: or file: prefix)
      maxResults - how many segments to retrieve (default 3)
      minScore   - minimum relevance threshold (default 0.5)
    Alternative: use .withRAG(DocumentSource...) for byte[] content

  @ActivityTracked                                       (see USE CASE 11)
    Where:    on a public method (in your service class)
    Purpose:  records a user-activity event when the method is called, so an
              assistant wired with .withActivityContext(...) can later resolve
              "this"/"that" from what the user just did
    Attributes:
      type           - event category (default BUSINESS_ACTION)
      verb           - the act, e.g. "view"/"approve" (default: method name)
      entityType     - the kind of entity touched, e.g. "order"
      entityIdParams - names of the parameter(s) carrying the entity id
      includeText    - capture a String parameter as free text (default false)
    Companion: @DynTab(trackActivity = true) records tab open/select navigation

================================================================================
  TIPS
================================================================================

  1. Start simple. Use EasyAI.chat() first to verify your API key works.

  2. System messages matter. A good system message dramatically improves results.
     Be specific: "You are a customer support agent for Acme Corp. Be concise."

  3. Tool methods should return Strings. The AI works best when your methods
     return human-readable strings. If your method returns an object,
     make sure it has a good toString().

  4. Memory size depends on use case. For quick Q&A, 10 is enough.
     For long conversations, use 30-50. More memory = higher API cost.

  5. For testing, use withChatModel() to inject a mock:
       Conversation chat = EasyAI.chat()
           .withChatModel(mockModel)
           .build();

  6. Temperature guide:
       0.0 = factual, deterministic (good for data lookups)
       0.3 = mostly factual with slight variation
       0.7 = balanced (good default for conversation)
       1.0 = creative (good for brainstorming, stories)

  7. EasyAgent tip: always use withStepListener() during development.
     Without it, tool calls are a black box — you won't know what the agent
     called, with what arguments, or what it got back. Log every step.

  8. Always wrap bot.ask(), chat.send(), and agent.execute() in try-catch in production code.
     AI calls can fail (network issues, rate limits, bad model output). Use
     EasyAI.extractErrorMessage(e) to get a clean, readable message instead
     of raw JSON from the provider:

       try {
           return bot.ask(userQuestion);
       } catch (Exception e) {
           log.error("AI call failed", e);
           return "Sorry, something went wrong: " + EasyAI.extractErrorMessage(e);
       }

     EasyAI.extractErrorMessage() parses the JSON error format used by
     OpenAI-compatible providers (OpenAI, Groq, Azure OpenAI) and extracts
     only the human-readable "message" field. For plain-text error messages
     (Ollama, network errors), it returns the message as-is.

     Common LangChain4J exceptions to catch separately if needed:
       dev.langchain4j.exception.AuthenticationException  - wrong API key
       dev.langchain4j.exception.RateLimitException       - rate limit exceeded
       dev.langchain4j.exception.InvalidRequestException  - bad request / tool call failure
       dev.langchain4j.exception.InternalServerException  - provider server error
